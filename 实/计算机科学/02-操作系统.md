# 操作系统

> "操作系统是计算机的灵魂——它隐于硬件之上、应用之下，以一套抽象让混乱的电路显得有序。" —— 化用 Tanenbaum

操作系统是介于硬件与应用之间的那一层系统软件。它管理 CPU 的分时、内存的分配、磁盘的读写、设备的驱动，并为上层程序提供一组统一的接口——系统调用。没有它，程序员须直接与寄存器、中断控制器、磁盘控制器打交道；有了它，"写文件""创建进程""发送网络包"皆成一行函数调用。本篇自操作系统的角色与历史起笔，经进程与线程的并发世界，入 CPU 调度的权衡艺术，再至内存管理的虚实之辨，终于文件系统的持久化与死锁安全之防——六篇既立，资源管理的全貌可窥。

---

## 一、操作系统概述

### 1.1 概念动机

裸机之上，程序直接操作硬件。当多个程序共用一台机器，谁先跑、谁等着、内存怎么分、打印机归谁用——若无仲裁者，必陷混乱。操作系统正是这个仲裁者。它以**资源管理者**的身份协调各方，又以**扩展机**的身份为程序员提供比硬件更友好的抽象：文件代替磁盘扇区，进程代替 CPU 寄存器，虚拟内存代替物理地址。

### 1.2 OS 的角色与功能

| 角色 | 功能 | 抽象层 |
|------|------|--------|
| 资源管理者 | CPU 调度、内存分配、设备驱动 | 进程、页、设备文件 |
| 扩展机 | 提供系统调用接口 | 文件、管道、套接字 |
| 保护者 | 隔离进程、权限控制 | 地址空间、用户/内核态 |

核心功能可归纳为五项：**进程管理**（创建、调度、同步）、**内存管理**（分配、回收、虚拟化）、**文件系统**（存储、目录、保护）、**设备管理**（驱动、中断、缓冲）、**用户接口**（Shell、系统调用、GUI）。

### 1.3 内核态与用户态

现代 CPU 通常提供至少两种执行模式：**内核态**（Kernel Mode）可执行所有指令、访问所有硬件；**用户态**（User Mode）受限，禁止直接操作 I/O 与特权指令。此隔离是安全的基石——一个用户程序的崩溃不会拖垮整个系统。

| 特性 | 内核态 | 用户态 |
|------|--------|--------|
| 特权指令 | 可执行（如 HLT、IN/OUT） | 禁止 |
| 内存访问 | 全部物理空间 | 仅自身地址空间 |
| 崩溃影响 | 系统宕机 | 仅该进程终止 |
| 运行者 | OS 内核、驱动 | 应用程序 |

状态切换由**中断**、**异常**或**系统调用**触发：用户态遇此三者，CPU 硬件自动切换至内核态并跳转到预设的中断处理入口，此过程称**trap**。

### 1.4 系统调用

**系统调用**（syscall）是用户程序请求内核服务的唯一正规通道。以 Linux 写文件为例：

```
用户程序 ──write(fd, buf, n)──→  软中断/syscall指令  ──→  内核: sys_write()
                                                              │
                                                              ↓
                                                        驱动写磁盘
                                                              │
                                                              ↓
                                                          返回用户态
```

POSIX 标准定义了约数百个系统调用，常用的有 `fork`、`exec`、`open`、`read`、`write`、`exit`、`wait`、`kill` 等。每次调用的开销包括：模式切换、参数拷贝、内核栈切换——约数百纳秒至数微秒，远高于普通函数调用。

### 1.5 OS 的历史脉络

| 时代 | 主导形态 | 代表系统 | 核心矛盾 |
|------|----------|----------|----------|
| 1950s | 批处理 | OS/360 | 吞吐量 vs 设备等待 |
| 1960s | 分时系统 | CTSS、Multics、Unix | 公平性 vs 响应时间 |
| 1970–80s | 个人机 | CP/M、MS-DOS、MacOS | 单用户 vs 资源有限 |
| 2000s | 移动 | iOS、Android | 功耗 vs 性能 |
| 2010s+ | 云/容器 | Linux 容器、Kubernetes | 隔离 vs 密度 |

批处理时代，作业排队依次执行，CPU 常因等待磁带而闲置。分时系统引入**时间片**，多个终端共享一台主机，每个用户仿佛独占。Unix（1969）诞生于贝尔实验室，以简洁的"文件—管道—工具"哲学影响至今。移动时代引入电源管理与沙箱应用模型；云时代则以容器技术将一台物理机切分为数百隔离单元。

### 1.6 主流操作系统对比

| 特性 | Linux | Windows | macOS | Android |
|------|-------|---------|-------|---------|
| 内核 | 宏内核 | 混合内核 | XNU（混合） | Linux（宏内核） |
| 文件系统 | ext4、XFS、Btrfs | NTFS、ReFS | APFS | ext4、F2FS |
| 图形子系统 | X11、Wayland | DWM | Quartz/CoreAnimation | SurfaceFlinger |
| 包管理 | apt、rpm | MSI、Store | App Store | APK、Play |
| 开源 | 是 | 否 | Darwin 部分 | AOSP 部分 |
| 主战场 | 服务器、嵌入式 | 桌面、企业 | 创意工作站 | 移动设备 |

## 二、进程与线程

### 2.1 概念动机

一个程序静卧磁盘时只是字节序列。当它被载入内存、获得 CPU 时间、开始执行指令，便成为一个动态的实体——进程。操作系统须在多个进程间公平而高效地分摊 CPU，同时保证它们互不干扰。进程的引入使"并发"成为可能：一台机器上同时跑浏览器、编辑器、音乐播放器，各自仿佛独占整台机器。

### 2.2 进程与 PCB

**进程**是程序在某个数据集合上的一次执行活动，是系统进行资源分配的基本单位。每个进程在内核中有一个**进程控制块**（Process Control Block, PCB），它是进程存在的唯一标识。

| PCB 字段 | 内容 |
|----------|------|
| 进程标识 | PID、PPID、UID、GID |
| 处理机状态 | 通用寄存器、PC、SP、PSW |
| 调度信息 | 状态、优先级、时间片、等待原因 |
| 资源信息 | 内存指针、打开文件表、信号掩码 |

PCB 在 Linux 中即 `task_struct`，约数千字节节，包含上述全部信息。调度器遍历 PCB 链表做出决策。

### 2.3 进程状态：五态模型

```
              创建
                │
                ↓
   ┌─────── 就绪 ←────────────┐
   │          │                │
   │     调度  │  时间片到      │
   │          ↓                │
   │       运行 ────等待事件──→ 阻塞
   │          │                │
   │       退出 │  事件完成      │
   │          ↓                │
   └────── 终止 ←──────────────┘
```

| 状态 | 含义 | 转移条件 |
|------|------|----------|
| 就绪 | 已具备运行条件，等待 CPU | 创建完成、时间片到、I/O 完成 |
| 运行 | 正在 CPU 上执行 | 被调度选中 |
| 阻塞 | 等待 I/O 或事件 | 请求 I/O、等待信号 |
| 创建 | 正在分配资源 | 初始化完成→就绪 |
| 终止 | 已结束，待回收 | 执行完毕或被杀死 |

运行→就绪的转变由**时钟中断**强制触发，保证公平。阻塞→就绪则由 I/O 完成中断驱动。

### 2.4 进程间通信

独立进程各自拥有地址空间，无法直接访问彼此内存。OS 提供 **IPC**（Inter-Process Communication）机制以实现数据交换与同步。

| 机制 | 原理 | 特点 |
|------|------|------|
| 管道 Pipe | 内核缓冲区字节流 | 父子进程间、半双工 |
| 命名管道 FIFO | 文件系统中的管道 | 无亲缘关系也可用 |
| 消息队列 | 内核维护的消息链表 | 有格式、可分类读取 |
| 共享内存 | 映射同一物理页 | 最快、须自行同步 |
| 信号量 Semaphore | 内核计数器 | 用于同步与互斥 |
| Socket | 网络协议栈端点 | 跨主机、最通用 |

共享内存速度最快——省去数据拷贝，但须配合信号量或互斥锁防止竞争。Socket 是唯一天然支持跨主机的机制，是网络通信的基础。

### 2.5 线程与进程

**线程**是进程内的执行单元，是 CPU 调度的基本单位。同一进程的线程共享地址空间与文件资源，但各有独立的栈与寄存器上下文。

| 对比项 | 进程 | 线程 |
|--------|------|------|
| 资源单位 | 资源分配的基本单位 | 调度的基本单位 |
| 地址空间 | 独立 | 共享所属进程 |
| 创建开销 | 大（复制地址空间） | 小（仅栈与寄存器） |
| 切换开销 | 大（切换页表/TLB） | 小（同地址空间内） |
| 通信方式 | IPC（管道、Socket） | 共享内存直接读写 |
| 崩溃影响 | 仅自身 | 拖垮整个进程 |

### 2.6 用户级线程与内核级线程

| 类型 | 管理 | 优点 | 缺点 |
|------|------|------|------|
| 用户级 | 用户库（如早期 pthreads） | 切换快、不陷内核 | 内核看不到，阻塞一个则全部阻塞 |
| 内核级 | 内核 | 可并行多核、阻塞不影响其他 | 切换须陷入内核 |

现代系统普遍采用**一对一模型**：每个用户线程对应一个内核线程，如 Linux 的 NPTL、Windows 线程。

### 2.7 线程同步

多线程共享内存，若无同步则竞争条件导致数据不一致。

| 原语 | 作用 | 典型用法 |
|------|------|----------|
| 互斥锁 Mutex | 保护临界区，同一时刻仅一个进入 | 更新共享计数器 |
| 信号量 Semaphore | 计数控制，N 个许可 | 限制并发连接数 |
| 条件变量 Condition Variable | 等待条件成立再唤醒 | 生产者-消费者 |
| 读写锁 RWLock | 读共享、写独占 | 缓存读多写少 |

互斥锁最常用。底层依赖硬件原子指令（如 x86 的 `LOCK CMPXCHG` 即 CAS），或关中断、自旋等待。条件变量须配合互斥锁使用：先加锁检查条件，不满足则等待并自动释放锁，被唤醒后重新加锁。

### 2.8 经典同步问题

**生产者-消费者**：缓冲区固定大小，生产者满则等，消费者空则等。以信号量解之：

- `empty` = 空槽数，初值 N
- `full` = 满槽数，初值 0
- `mutex` = 缓冲区互斥，初值 1

生产者：`P(empty); P(mutex); 放入; V(mutex); V(full)`
消费者：`P(full); P(mutex); 取出; V(mutex); V(empty)`

**读者-写者**：多读者可并发读，写者须独占。以读写锁或信号量实现，注意写者饥饿问题——读者源源不断时写者永等，须引入写优先策略。

**哲学家就餐**：五位哲学家围坐，每人左右各一筷，需两筷才能进食。若同时拿左筷再等右筷，必成死锁。解法：限制至多四人同时拿筷、或奇偶号哲学家拿筷顺序相反、或引入管程统一分配。

## 三、CPU 调度

### 3.1 概念动机

CPU 是系统最稀缺的资源之一。当就绪进程数多于 CPU 核心数，调度器须决定谁先跑、跑多久。好的调度策略在公平与效率间取得平衡：既不饿死任何进程，又使系统吞吐量高、响应快。

### 3.2 调度的三个层次

| 层次 | 频率 | 职责 |
|------|------|------|
| 长期调度 | 秒~分 | 决定哪些作业从外存调入内存成为进程 |
| 中期调度 | 秒 | 内存紧张时将进程换出至交换区（挂起） |
| 短期调度 | 毫秒~微秒 | 从就绪队列选一个进程分配 CPU |

长期调度控制**多道程序度**（内存中进程数），太高则内存紧张、太低则 CPU 闲置。短期调度最频繁，直接决定响应速度，是调度的核心。

### 3.3 调度算法对比

| 算法 | 策略 | 抢占 | 优点 | 缺点 |
|------|------|------|------|------|
| FCFS | 先来先服务 | 否 | 简单公平 | 短作业等长作业（护航效应） |
| SJF | 最短作业优先 | 否 | 平均等待最短 | 长作业饥饿、需预知时长 |
| SRTF | 最短剩余优先 | 是 | SJF 的抢占版 | 长作业更易饥饿 |
| RR | 时间片轮转 | 是 | 响应快、公平 | 时间片太小则切换开销大 |
| 优先级 | 按优先级选 | 可选 | 灵活 | 低优先级饥饿（用老化缓解） |
| MLFQ | 多级反馈队列 | 是 | 兼顾交互与批处理 | 参数调优复杂 |

**多级反馈队列**（MLFQ）是工程上最精巧的经典算法。它设多个优先级层：新进程入最高层，用完时间片后降一层，I/O 密集型进程因用不满时间片而留在高层——于是交互式应用获得快响应，CPU 密集型作业逐渐下沉到低层批处理。Windows 早期及许多 Unix 变体均采用其变体。

### 3.4 调度评价指标

| 指标 | 定义 |
|------|------|
| 吞吐量 | 单位时间完成的进程数 |
| 周转时间 | 从提交到完成的总时间 |
| 等待时间 | 就绪队列中等待的总时间 |
| 响应时间 | 从提交到首次响应的时间 |

交互式系统重响应时间，批处理系统重吞吐量。二者有时冲突：RR 响应快但切换多致吞吐略降。

### 3.5 实时调度

实时系统要求任务在**截止期**内完成。硬实时错过会导致灾难（如刹车系统），软实时允许偶尔超时（如视频播放）。

| 算法 | 策略 | 调度方式 | 可调度条件 |
|------|------|----------|------------|
| 速率单调 RM | 周期越短优先级越高 | 静态优先级、抢占 | $\sum \frac{C_i}{T_i} \le n(2^{1/n}-1)$ |
| 最早截止优先 EDF | 截止期最近者先 | 动态优先级、抢占 | $\sum \frac{C_i}{T_i} \le 1$ |

EDF 理论上可调度到 100% 利用率，但动态优先级开销大。RM 简单稳定，工业界更常用。

### 3.6 Linux CFS 调度器

**完全公平调度器**（Completely Fair Scheduler, CFS）自 Linux 2.6.23 起为默认调度类。其理念是"完美公平"的理想：每个进程按权重瓜分 CPU 时间。

- 数据结构：以**红黑树**组织就绪进程，键为虚拟运行时间 `vruntime`
- `vruntime` = 实际运行时间 ×（nice 0 的权重 / 该进程权重）
- nice 值越低权重越大，`vruntime` 增长越慢，分到更多 CPU
- 调度器始终选 `vruntime` 最小者（红黑树最左叶）

CFS 没有固定时间片，而以**目标延迟**（target latency）为周期：周期内每个就绪进程至少跑一次。进程数增多则单次时间缩短，但公平性保持。

## 四、内存管理

### 4.1 概念动机

内存是 CPU 直接寻址的存储，稀缺且宝贵。多个进程共存于内存，须防止互相越界；程序所需空间可能超过物理内存，须以某种方式"放大"可用容量。内存管理的本质是：在有限的物理空间上，为每个进程提供独立、充足、安全的地址空间。

### 4.2 连续分配与碎片

最朴素的方案是将内存划分为若干分区，每区放一个进程。

| 分配策略 | 方法 | 碎片 |
|----------|------|------|
| 固定分区 | 预设等大或大小不等分区 | 内部碎片 |
| 动态分区 | 按需分配恰好大小 | 外部碎片 |

**内部碎片**：分区大于进程，余量浪费。**外部碎片**：频繁分配回收后内存中布满小空洞，虽总量够但无法容纳大进程。紧凑可消除外部碎片，但移动数据开销大。

### 4.3 分页机制

分页将进程的逻辑地址空间分为固定大小的**页**（page），物理内存分为同等大小的**帧**（frame），以页表建立映射。页大小通常 4KB。

| 地址字段 | 位宽（4KB 页） | 含义 |
|----------|----------------|------|
| 页号 p | 高 20 位 | 索引页表 |
| 页内偏移 d | 低 12 位 | 页内地址 |

**页表**由页表项（PTE）组成，每项含物理帧号与状态位（有效、读写、脏、访问）。地址翻译：`逻辑地址 → 查页表 → 物理帧号 + 偏移`。

**TLB**（Translation Lookaside Buffer）是页表的高速缓存，缓存近期使用的 PTE。若无 TLB，每次访存须先读页表——多一次内存访问。TLB 命中率通常 > 99%，将翻译开销降至接近零。

**多级页表**：32 位单级页表需 4MB/进程，不现实。将页表分级——如 x86 的二级：页目录→页表——只为实际使用的页分配 PTE，节省内存。64 位系统用四级甚至五级页表。

### 4.4 分段与段页式

**分段**按程序的逻辑结构划分：代码段、数据段、栈段，各段大小可变。地址 = 段号 + 段内偏移。分段有利于共享与保护（代码段只读共享），但产生外部碎片。

**段页式**结合二者：先分段再分页。逻辑地址 = 段号 + 页号 + 偏移。既有逻辑清晰性又消除了外部碎片，代价是两次查表。x86 在保护模式下支持段页式，但现代 OS 将基段设为全覆盖，实质退化为纯分页。

### 4.5 虚拟内存与请求分页

**虚拟内存**使进程的逻辑地址空间可远大于物理内存。其法是**请求分页**：页表项标记"有效/无效"，访问无效页（不在内存）触发**缺页中断**，内核从磁盘调入该页、更新页表、恢复执行。

- 仅将当前需要的页调入内存，其余驻留磁盘（交换区或文件）
- 进程启动时几乎不占内存，随执行逐步按需调入
- 程序的局部性原理保证了可行性：访问集中在少数页

### 4.6 页面置换算法

内存满时须选一页换出。置换算法的选择直接影响缺页率。

| 算法 | 策略 | 优点 | 缺点 |
|------|------|------|------|
| OPT | 换出未来最久不用的页 | 理论最优 | 无法实现（需预知未来） |
| FIFO | 换出最先调入的页 | 简单 | 忽略访问模式，可能换出常用页 |
| LRU | 换出最久未访问的页 | 接近 OPT | 实现须维护时间戳，开销大 |
| Clock | 环形扫描，访问位为 0 则换出 | 近似 LRU 且高效 | 偶有偏差 |
| Second-Chance | FIFO + 访问位二次机会 | 改进 FIFO | 仍可能扫描多轮 |

**Clock 算法**（时钟/二次机会）：所有页组成环形链表，指针扫描。遇到访问位为 1 的页，清零并跳过（给"第二次机会"）；为 0 则换出。硬件每次访问自动置访问位为 1。Clock 是 LRU 的高效近似，Linux 与许多系统采用其变体。

### 4.7 Belady 异常

**Belady 异常**：FIFO 算法在增加物理帧数时，缺页率反而上升。这是 FIFO 唯一的怪癖——某些访问序列下，更多帧反而使旧页被更晚换出，干扰后续命中。LRU 与 OPT 不会出现此异常。

### 4.8 颠簸与工作集

**颠簸**（thrashing）是指进程频繁缺页，CPU 大量时间用于换页而非计算，吞吐骤降。成因：内存中进程过多，每个分到的帧少于其工作集。

**工作集**（Working Set）是进程在某时间窗口 $\Delta$ 内访问的页面集合，代表其"近期活跃足迹"。Denning 的理论指出：只有当分配帧数 ≥ 工作集大小，进程才能高效运行。防颠簸的策略包括：挂起部分进程降低多道程序度、采用工作集模型或缺页频率反馈调节。

## 五、文件系统

### 5.1 概念动机

内存断电即失，磁盘方能持久。文件系统是组织磁盘上数据的规则：它将字节序列抽象为"文件"，将文件组织为"目录"，并管理元数据、权限、空间分配。一个好的文件系统须在性能、可靠性、空间利用率之间取得平衡。

### 5.2 文件属性与类型

文件是一组带名称的相关数据集合。除数据本身外，还有**属性**（元数据）：

| 属性 | 说明 |
|------|------|
| 名称 | 唯一标识（目录内） |
| 类型 | 普通文件、目录、设备、链接 |
| 大小 | 当前大小与已分配空间 |
| 权限 | rwx，属主/组/其他 |
| 时间戳 | 创建、修改、访问 |

Unix 的"一切皆文件"哲学将设备、管道、套接字统一为文件接口，简化编程模型。

### 5.3 目录结构

| 结构 | 特点 | 问题 |
|------|------|------|
| 单级 | 全部文件同一目录 | 命名冲突、难管理 |
| 二级 | 每用户一目录 | 不够灵活 |
| 树形 | 层次结构，唯一路径 | 文件只能属一目录 |
| 无环图 DAG | 允许共享（链接） | 遍历与删除需特殊处理 |

树形目录是主流方案。DAG 通过**硬链接**（多个路径指向同一 inode）或**符号链接**（特殊文件含目标路径）实现共享。硬链接不能跨文件系统且不能链接目录，符号链接则更灵活但多一次寻址。

### 5.4 文件的物理结构

| 结构 | 方式 | 优点 | 缺点 |
|------|------|------|------|
| 连续分配 | 紧邻存储 | 顺序读写快、简单 | 碎片严重、难增长 |
| 链接分配 | 每块含下一块指针 | 无外部碎片、易增长 | 随机访问慢、指针损坏致命 |
| 索引分配 | 索引块记录所有数据块位置 | 随机访问快 | 索引开销、大文件需多级索引 |

索引分配是现代文件系统的主流。大文件用**多级索引**（如 ext2/3/4 的 12 直接 + 1 间接 + 1 双间接 + 1 三间接），兼顾小文件效率与大文件容量。

### 5.5 主流文件系统对比

| 特性 | FAT32 | NTFS | ext4 | APFS |
|------|-------|------|------|------|
| 最大文件 | 4GB | 16EB | 16TB | 8EB |
| 日志 | 无 | 有 | 有 | 有（Copy-on-Write） |
| 权限 | 简单 | ACL | POSIX ACL | POSIX + 加密 |
| 快照 | 无 | VSS | 有（LVM 层） | 原生快照 |
| 误删恢复 | 弱 | 卷影副本 | 无原生 | 快照回滚 |
| 主战场 | U 盘 | Windows | Linux | Apple 全线 |

FAT32 虽古老但兼容性最好，U 盘与嵌入式仍常见。NTFS 引入日志与安全描述符。ext4 是 Linux 桌面与服务器默认。APFS 为 SSD 时代设计，以写时复制实现快照与空间共享。

### 5.6 虚拟文件系统

**VFS**（Virtual File System）是内核中的一层抽象，为各类具体文件系统提供统一接口。应用程序调用 `open`、`read`、`write`，不须关心底层是 ext4 还是 NFS。

```
应用 ──open/read/write──→ VFS ──→ ext4 / NTFS / NFS / proc
                              │
                          统一接口: inode, dentry, file_operations
```

VFS 定义四大对象：`superblock`（文件系统整体）、`inode`（文件元数据）、`dentry`（目录项）、`file`（打开的文件实例）。每种文件系统实现这些操作函数，即可接入 VFS。

### 5.7 日志型文件系统

崩溃可能发生在写操作的半途，导致文件系统不一致。**日志**（journaling）的核心思想是：先将要做的修改写入日志区，再执行实际修改。崩溃后只需重放日志或回滚，无需全盘扫描。

| 日志模式 | 写入策略 | 性能 | 安全 |
|----------|----------|------|------|
| Journal | 数据+元数据均入日志 | 慢 | 最高 |
| Ordered | 元数据入日志，数据先写 | 中 | 高 |
| Writeback | 仅元数据入日志，数据无序 | 快 | 可能旧数据 |

ext4 默认 Ordered 模式，兼顾安全与性能。NTFS、XFS、JFS 亦为日志型。

### 5.8 RAID 与容错

磁盘是机械部件，故障率不低。**RAID**（Redundant Array of Independent Disks）将多盘组合为逻辑卷，提升性能与可靠性。

| 级别 | 机制 | 冗余 | 最少盘数 |
|------|------|------|----------|
| RAID 0 | 条带化 | 无 | 2 |
| RAID 1 | 镜像 | 1 份 | 2 |
| RAID 5 | 条带+分布式奇偶 | 1 盘容忍 | 3 |
| RAID 6 | 条带+双重奇偶 | 2 盘容忍 | 4 |
| RAID 10 | 镜像+条带 | 每组 1 盘 | 4 |

RAID 5 读写性能与空间利用率兼顾，是中小型阵列常用方案。RAID 6 容忍双盘同时故障，适合大阵列以降低重建期二次故障风险。

## 六、死锁与安全

### 6.1 概念动机

并发是效率的源泉，也是祸根。多个进程争抢资源，若互相持有对方所需又不肯让步，便陷入僵局——这就是**死锁**（deadlock）。一旦发生，涉事进程全部冻结，除非外力介入或超时。理解死锁的成因与防范，是系统设计的必修课。

### 6.2 死锁的四个必要条件

Coffman 于 1971 年证明，死锁发生须同时满足四个条件：

| 条件 | 含义 |
|------|------|
| 互斥 Mutual Exclusion | 资源在同一时刻只能被一个进程占用 |
| 占有并等待 Hold and Wait | 进程持有资源同时等待另一资源 |
| 不剥夺 No Preemption | 资源不能被强制夺走，只能自愿释放 |
| 循环等待 Circular Wait | 存在进程的环形等待链 |

四者缺一，死锁不成立。这是预防死锁的理论基础——破坏任一条件即可。

### 6.3 死锁处理策略

| 策略 | 思路 | 代价 | 实例 |
|------|------|------|------|
| 鸵鸟 Ostrich | 忽略，假装不会发生 | 无 | Linux、Windows 桌面 |
| 预防 Prevention | 破坏四条件之一 | 资源利用率低 | 一次性申请所有资源 |
| 避免 Avoidance | 运行时判断是否安全 | 须预知最大需求 | 银行家算法 |
| 检测 Detection | 周期扫描资源图 | 开销与复杂性 | 数据库死锁检测 |
| 恢复 Recovery | 杀进程或剥夺资源 | 丢失工作 | 选牺牲者回滚 |

鸵鸟策略看似荒唐，却是大多数通用 OS 的选择——死锁概率低、预防代价高，不如重启了事。数据库等高要求场景才采用检测与恢复。

### 6.4 银行家算法

Dijkstra 提出。类比银行贷款：银行家有限资金，客户各报最大需求，每次借款须判断分配后是否仍存在安全序列——即所有客户能以某种顺序依次完成并还回资金。

- 数据结构：`Available`（各资源剩余）、`Max`（各进程最大需求）、`Allocation`（已分配）、`Need` = Max − Allocation
- 安全性检查：找一 Need ≤ Available 的进程，模拟其完成释放资源，重复至全部完成则安全
- 每次请求资源，先试分配，再检查安全性，安全则批准，否则等待

银行家算法保证了系统永不进入不安全状态，从而永不死锁。代价是须预知最大需求、每次分配都要运算——实际系统中很少完全采用，但作为理论与考试经典流传。

### 6.5 资源分配图

以有向图刻画进程与资源的关系：进程→资源表示请求，资源→进程表示分配。若图中无环，系统必无死锁；若每类资源仅一个实例，有环则有死锁。多实例时，有环不一定死锁，需进一步化简检查。

### 6.6 Linux 容器与安全隔离

传统隔离靠进程级地址空间。**容器**技术（Docker、containerd）走得更远：不虚拟化硬件，而在同一内核上以**namespace**与**cgroup**实现隔离与限流。

| namespace | 隔离对象 |
|-----------|----------|
| PID | 进程号 |
| Mount | 文件系统挂载点 |
| NET | 网络栈、网卡、路由 |
| IPC | 信号量、消息队列、共享内存 |
| UTS | 主机名、域名 |
| USER | UID/GID 映射 |

`cgroup`（Control Group）则限制 CPU、内存、I/O 带宽等资源用量。二者结合使容器拥有"轻量虚拟机"的效果：启动秒级、密度极高。安全方面，容器共享内核，若内核有漏洞则隔离可被穿透——不如虚拟机的硬件级隔离坚固，故高安全场景须配 seccomp、AppArmor、SELinux 等加固。

### 6.7 可信计算与 TEE

**可信执行环境**（Trusted Execution Environment, TEE）是 CPU 内一块隔离的"安全飞地"，即使内核被攻破，飞地内的代码与数据仍受硬件保护。

| 技术 | 厂商 | 机制 |
|------|------|------|
| SGX | Intel | 内存加密的 Enclave |
| TrustZone | ARM | 安全世界与非安全世界 |
| SEV-SNP | AMD | 虚拟机级内存加密 |

TEE 用于保护密钥、生物特征、区块链智能合约等敏感计算。**可信平台模块**（TPM）则提供硬件级密钥存储与度量启动（Boot Integrity），确保系统从上电到 OS 启动未被篡改。可信计算的核心理念是：**信任须有根，且根在硬件**——从 TPM 这一根 of trust 出发，逐级度量、逐级签名，构建一条可信链。

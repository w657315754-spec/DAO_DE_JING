# 数据库系统

> 数据是信息时代的石油,而数据库系统则是炼油厂。从文件系统的冗余与不一致,到关系模型的优雅数学基础,再到分布式与 NewSQL 的全球扩展,数据库技术的演进始终围绕一个核心命题:如何在持久化、共享、并发的前提下,兼顾一致性、可用性与性能。本文以六节篇幅,系统梳理数据库领域的理论、工程与实践。

---

## 一、数据库概述与关系模型

### 1.1 文件系统 vs 数据库系统

早期的数据管理依赖文件系统,应用程序直接读写操作系统文件。这种方式存在数据冗余、不一致、并发访问困难、缺乏安全性等痼疾。数据库系统通过统一的 DBMS 管理数据,实现数据共享与程序与数据的解耦。

| 对比维度 | 文件系统 | 数据库系统 |
|---------|---------|-----------|
| 数据冗余 | 高,各应用各自存储 | 低,统一管理共享 |
| 数据独立性 | 差,程序与文件结构耦合 | 强,三级模式与映像保障 |
| 并发控制 | 无,需自行加锁 | 内置锁与 MVCC |
| 安全性 | 依赖 OS 权限 | 细粒度用户/角色授权 |
| 数据一致性 | 难以保证 | 约束、触发器、事务保障 |
| 查询能力 | 需编程实现 | 声明式 SQL |

### 1.2 DBMS 的核心功能

DBMS(Database Management System)是位于用户与操作系统之间的一层数据管理软件,提供数据定义、组织、存储、操纵、维护等能力。典型功能包括:

- **数据定义**:提供 DDL 描述数据结构、完整性约束。
- **数据操纵**:提供 DML 实现增删改查。
- **数据控制**:权限授予、事务管理、并发控制、恢复机制。
- **数据字典**:存储元数据,描述数据的结构与语义。

代表产品:Oracle、MySQL、PostgreSQL、SQL Server、DB2。

### 1.3 三级模式 ANSI-SPARC 体系结构

ANSI-SPARC 架构将数据库抽象为三级模式,是实现数据独立性的理论基础。

| 模式层级 | 别名 | 面向对象 | 说明 |
|---------|------|---------|------|
| 外模式(External Schema) | 用户模式 / 视图层 | 特定用户/应用 | 局部逻辑结构,屏蔽无关字段 |
| 概念模式(Conceptual Schema) | 逻辑模式 | 全局用户 | 全局逻辑结构与约束 |
| 内模式(Internal Schema) | 存储模式 | DBMS 内部 | 物理存储结构、索引、路径 |

### 1.4 两级映像与数据独立性

三级模式之间通过两级映像实现数据独立性:

- **外模式/概念模式映像**:保证逻辑数据独立性。当概念模式变化(如字段重命名),只需修改映像,外模式保持不变。
- **概念模式/内模式映像**:保证物理数据独立性。当内模式变化(如更换存储结构、调整索引),概念模式保持不变。

这种分离使得应用程序无需关心存储细节,是数据库系统区别于文件系统的根本特征。

### 1.5 关系模型基本概念

1970 年 Codd 提出关系模型,以集合论为基础,将数据组织为二维表。核心概念:

- **关系(Relation)**:一个表,对应一个实体集。
- **元组(Tuple)**:表中一行,对应一条记录。
- **属性(Attribute)**:表中一列,对应一个字段。
- **域(Domain)**:属性的取值范围,具有原子性。
- **键(Key)**:
  - **候选键(Candidate Key)**:能唯一标识元组且无冗余的属性组。
  - **主键(Primary Key)**:从候选键中选定一个。
  - **外键(Foreign Key)**:引用其他关系主键,实现参照完整性。
  - **超键(Super Key)**:能唯一标识元组的属性组,可含冗余属性。

关系模型要求满足三类完整性约束:**实体完整性**(主键非空)、**参照完整性**(外键要么空要么存在)、**用户定义完整性**(业务约束)。

### 1.6 关系代数

关系代数是关系模型的过程化查询语言,以关系为运算对象,结果仍为关系。

| 运算 | 符号 | 语义 |
|------|------|------|
| 选择(Selection) | σ | 按条件筛选行 σ_{age>20}(Student) |
| 投影(Projection) | π | 选取指定列 π_{name,age}(Student) |
| 连接(Join) | ⋈ | 按条件合并两表 R ⋈_{R.id=S.id} S |
| 除(Division) | ÷ | 查询"全部"语义 R ÷ S |
| 并/差/笛卡尔积 | ∪ / − / × | 集合运算 |

自然连接(Natural Join)在等值连接基础上自动去重复列。除运算适用于"查询选修了所有课程的学生"这类全称量词问题。

### 1.7 SQL 语言分类

SQL(Structured Query Language)是关系数据库的标准语言,按功能分为五类:

| 类别 | 全称 | 关键字 | 作用 |
|------|------|--------|------|
| DDL | Data Definition Language | CREATE / ALTER / DROP | 定义模式、表、索引 |
| DML | Data Manipulation Language | INSERT / UPDATE / DELETE | 操作数据 |
| DQL | Data Query Language | SELECT | 查询数据 |
| DCL | Data Control Language | GRANT / REVOKE | 权限控制 |
| TCL | Transaction Control Language | COMMIT / ROLLBACK / SAVEPOINT | 事务管理 |

DQL 严格说是 DML 的子集,实践中常单列。SQL 是非过程化的声明式语言,优化器负责将其翻译为最优执行计划。

## 二、SQL 与查询优化

### 2.1 SQL 基础 CRUD

CRUD 对应 Create、Read、Update、Delete,是数据操作的基石。

```sql
-- Create
INSERT INTO Student(id, name, age) VALUES (1, '张三', 20);
-- Read
SELECT id, name FROM Student WHERE age > 18;
-- Update
UPDATE Student SET age = 21 WHERE id = 1;
-- Delete
DELETE FROM Student WHERE id = 1;
```

### 2.2 JOIN 类型对比

连接(JOIN)用于组合多表数据,是关系模型关联能力的体现。

| JOIN 类型 | 结果集 | 行为 |
|-----------|-------|------|
| INNER JOIN | 交集 | 只返回两表匹配的行 |
| LEFT [OUTER] JOIN | 左表全部 + 匹配 | 左表无匹配则右表为 NULL |
| RIGHT [OUTER] JOIN | 右表全部 + 匹配 | 右表无匹配则左表为 NULL |
| FULL [OUTER] JOIN | 并集 | 两表无匹配处补 NULL |
| CROSS JOIN | 笛卡尔积 | 返回 m×n 行 |

### 2.3 子查询 vs 连接

子查询嵌套于 SELECT/FROM/WHERE,语义清晰但可能性能较差;连接(JOIN)由优化器统一处理,通常更高效。现代优化器常将相关子查询改写为半连接(Semi-Join)或聚合下推。

- **非相关子查询**:独立执行一次,如 `WHERE id IN (SELECT id FROM B)`。
- **相关子查询**:每行重新执行,如 `WHERE score > (SELECT AVG(score) FROM B WHERE B.class = A.class)`。

### 2.4 聚合函数与分组

聚合函数对集合计算单值:COUNT、SUM、AVG、MAX、MIN。

- `GROUP BY`:按列分组,SELECT 中非聚合列必须出现在分组中。
- `HAVING`:对分组结果过滤,区别于 WHERE 对行过滤。
- 执行顺序:FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT。

### 2.5 窗口函数

窗口函数(Window Function)在不折叠行的前提下进行聚合或排名计算,语法为 `函数() OVER (PARTITION BY ... ORDER BY ...)`。

| 函数 | 语义 |
|------|------|
| ROW_NUMBER() | 无重复连续行号 |
| RANK() | 并列后跳号 |
| DENSE_RANK() | 并列后不跳号 |
| LAG(col, n) | 当前行之前第 n 行值 |
| LEAD(col, n) | 当前行之后第 n 行值 |
| SUM/AVG OVER | 累计/滑动聚合 |

典型场景:计算用户连续登录天数、各班级成绩排名、环比增长率。

### 2.6 查询优化:逻辑优化 vs 物理优化

查询优化器(Query Optimizer)将 SQL 转换为高效执行计划,分两层:

- **逻辑优化**:基于关系代数等价变换,如选择下推、投影裁剪、连接顺序重排、子查询消除。目标:减少中间结果规模。
- **物理优化**:为逻辑算子选择具体实现,如顺序扫描 vs 索引扫描、Hash Join vs Nested Loop vs Merge Join。目标:最小化执行代价。

### 2.7 RBO vs CBO

| 优化方式 | 全称 | 原理 | 缺点 |
|---------|------|------|------|
| RBO | Rule-Based Optimization | 基于预设规则,如"索引优先于全表" | 忽略数据分布,可能选错计划 |
| CBO | Cost-Based Optimization | 基于统计信息估算代价选择最优 | 依赖统计准确性,需定期 ANALYZE |

现代数据库普遍采用 CBO,如 PostgreSQL、MySQL 8.0+、Oracle。统计信息包括表的行数、列基数(Cardinality)、直方图分布、NULL 比例等。

### 2.8 执行计划与索引选择性

使用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 查看执行计划,关键指标:

- **访问路径**:Seq Scan / Index Scan / Index Only Scan / Bitmap Heap Scan。
- **连接算法**:Nested Loop(适合小表或带索引)、Hash Join(适合大表等值)、Merge Join(已排序输入)。
- **代价估算**:startup cost 与 total cost。

**索引选择性** = 不同值数量 / 总行数,选择性越高越适合建索引。**基数**(Cardinality)指列不同值的数量,是 CBO 估算行数的关键。低基数列(如性别)不适合 B+ 树索引,可考虑位图索引。

## 三、事务与并发控制

### 3.1 ACID 四特性

事务(Transaction)是数据库操作的逻辑执行单元,满足 ACID:

| 特性 | 全称 | 含义 | 实现机制 |
|------|------|------|---------|
| 原子性 Atomicity | Atomicity | 全做或全不做 | Undo Log 回滚 |
| 一致性 Consistency | Consistency | 事务前后满足约束 | 约束 + AID 共同保障 |
| 隔离性 Isolation | Isolation | 并发事务互不干扰 | 锁 / MVCC |
| 持久性 Durability | Durability | 提交后永久 | Redo Log + WAL |

### 3.2 并发问题

| 问题 | 描述 | 示例 |
|------|------|------|
| 脏读 Dirty Read | 读到未提交的数据 | T1 更新后回滚,T2 已读到旧值 |
| 不可重复读 Non-Repeatable Read | 同一查询两次结果不同 | T2 两次读之间 T1 修改了行 |
| 幻读 Phantom Read | 同一查询两次返回行数不同 | T2 两次范围查询间 T1 插入新行 |
| 丢失更新 Lost Update | 两事务覆盖彼此更新 | T1、T2 都基于旧值更新 |

### 3.3 隔离级别对比

SQL 标准定义四级隔离级别,从弱到强:

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现代价 |
|---------|------|-----------|------|---------|
| 读未提交 Read Uncommitted | 可能 | 可能 | 可能 | 最低 |
| 读已提交 Read Committed | 避免 | 可能 | 可能 | 低 |
| 可重复读 Repeatable Read | 避免 | 避免 | 可能(InnoDB 避免) | 中 |
| 串行化 Serializable | 避免 | 避免 | 避免 | 高,性能差 |

Oracle 默认 Read Committed,MySQL InnoDB 默认 Repeatable Read(通过 Next-Key Lock 解决幻读),PostgreSQL 默认 Read Committed。

### 3.4 锁机制

| 锁类型 | 符号 | 兼容性 | 用途 |
|-------|------|--------|------|
| 共享锁 Shared Lock | S | 与 S 兼容,与 X 互斥 | 读操作 |
| 排他锁 Exclusive Lock | X | 与所有锁互斥 | 写操作 |
| 意向共享锁 Intent Shared | IS | 表级,与 IX 兼容 | 表锁前声明行 S 锁 |
| 意向排他锁 Intent Exclusive | IX | 表级,与 IS/S 兼容 | 表锁前声明行 X 锁 |
| 更新锁 Update Lock | U | 与 S 兼容,防死锁 | 预升级 X 锁 |

意向锁是表级锁,用于快速判断表上是否有行锁,避免逐行扫描。InnoDB 还有 Record Lock(行锁)、Gap Lock(间隙锁)、Next-Key Lock(行+间隙锁)。

### 3.5 两阶段锁协议 2PL

两阶段锁定(Two-Phase Locking)保证冲突可串行化:

1. **增长阶段**:事务获取锁,不释放。
2. **收缩阶段**:事务释放锁,不再获取。

严格 2PL(Strict 2PL)要求 X 锁持有至事务结束,避免级联回滚。2PL 是可串行化的充分条件,但可能产生死锁。

### 3.6 MVCC 多版本并发控制

MVCC(Multi-Version Concurrency Control)通过为每行保存多个版本,实现"读不阻塞写,写不阻塞读"。核心要素:

- **版本链**:每行隐藏字段记录前版本指针,形成链表。
- **事务 ID 与可见性**:每版本标记创建/删除事务 ID,通过 Read View 判断可见性。
- **Read View**:快照,记录活跃事务列表,决定读哪个版本。

InnoDB 在 RC 级别每条 SQL 生成新 Read View,在 RR 级别事务首次读时生成并复用。PostgreSQL 使用类似 xmin/xmax 机制。

### 3.7 快照隔离与 SSI

**快照隔离(Snapshot Isolation, SI)**:事务读一致性快照,写基于旧值,提交时检查写写冲突。可避免幻读,但存在**写倾斜(Write Skew)**异常:两事务各自读对方未修改的行并各自写入,导致业务约束被破坏。

**可串行化快照隔离(SSI, Serializable Snapshot Isolation)**:在 SI 基础上追踪读写依赖,检测并发执行的危险结构(srw 依赖环),回滚部分事务。PostgreSQL 9.1+ 的 Serializable 即基于 SSI 实现,性能优于传统表锁串行化。

### 3.8 死锁检测与预防

死锁产生条件:互斥、请求保持、不剥夺、循环等待。

- **预防**:一次性申请所有锁(破坏请求保持)、按序加锁(破坏循环等待)、锁超时自动回滚。
- **检测**:等待图(Wait-For Graph)检测环,InnoDB 使用主动死锁检测回滚代价较小的事务。
- **避免**:银行家算法,但实现复杂,实践中少用。

## 四、索引与存储

### 4.1 B 树 vs B+ 树

| 对比项 | B 树 | B+ 树 |
|-------|------|-------|
| 数据存储 | 所有节点均存数据 | 仅叶子节点存数据 |
| 叶子链表 | 无 | 双向链表相连 |
| 范围查询 | 需中序遍历 | 顺序扫描叶子链表 |
| 非叶节点 | 存键 + 数据 | 仅存键 + 指针 |
| 单点查询 | 可能命中内部节点 | 必到叶子 |
| 树高 | 略低 | 略高,但扇出大 |

B+ 树因非叶节点不存数据,扇出更大,树高更低,且叶子链表利于范围查询,是关系数据库索引的主流选择(MySQL InnoDB、PostgreSQL、Oracle)。

### 4.2 聚簇索引 vs 非聚簇索引

- **聚簇索引(Clustered Index)**:叶子节点直接存储完整行数据,数据物理有序,每表仅一个。InnoDB 主键索引即聚簇索引。
- **非聚簇索引(Secondary Index)**:叶子节点存储主键值,需回表查询完整行。一张表可有多个。

InnoDB 选择主键作为聚簇键,无主键则用唯一非空索引,再无则隐式生成 ROW_ID。SQL Server 允许显式指定 CLUSTERED/NONCLUSTERED。

### 4.3 覆盖索引与回表

- **回表(Table Lookup)**:二级索引查到主键后再查聚簇索引取行数据,两次 IO。
- **覆盖索引(Covering Index)**:索引包含查询所需全部列,无需回表。`SELECT name, age FROM t WHERE name=?` 若在 (name, age) 上建索引则被覆盖。

InnoDB 支持索引下推(Index Condition Pushdown, ICP),在存储引擎层过滤,减少回表次数。

### 4.4 联合索引与最左前缀匹配

联合索引(Composite Index)如 (a, b, c) 按 a→b→c 排序存储,遵循**最左前缀匹配**原则:

- `WHERE a=? AND b=?` 命中。
- `WHERE a=? AND c=?` 仅 a 命中,c 无法利用索引(中间断档)。
- `WHERE b=?` 不命中(缺少最左列 a)。

范围查询(>、<、LIKE 'x%')右侧列失效。设计索引应将等值列置前、范围列置后。

### 4.5 哈希索引

哈希索引基于哈希表,等值查询 O(1),但不支持范围查询、排序、最左前缀。Memory 引擎原生支持;InnoDB 自适应哈希索引(Adaptive Hash Index)对热点 B+ 树页自动建哈希。MySQL 仅 Memory/Heap 支持;PostgreSQL 不内置哈希索引(可扩展)。

### 4.6 位图索引

位图索引(Bitmap Index)为每个键值维护位图,位图每位对应一行是否为此值。适合低基数列(性别、状态),高并发写入性能差,适合 OLAP。Oracle 支持位图索引,MySQL/PostgreSQL 不原生支持。

### 4.7 倒排索引与全文搜索

倒排索引(Inverted Index)由词项映射到文档列表,是全文检索引擎的核心:

- **词典(Term Dictionary)**:词项集合,可用 FST 优化。
- ** postings list**:每个词对应的文档 ID 列表,可用 Roaring Bitmap 压缩。
- **位置信息**:支持短语查询与高亮。

Elasticsearch、Lucene、Solr 均基于倒排索引。PostgreSQL 的 tsvector/tsquery 提供 GIN 倒排索引支持全文搜索。

### 4.8 LSM 树与列式存储

**LSM 树(Log-Structured Merge Tree)**:写入先入 MemTable(内存有序结构),满后刷盘为 SSTable,后台 Compaction 合并多层。写性能极高,读需合并多层,适合写密集场景。RocksDB、LevelDB、Cassandra、HBase、InfluxDB 均采用。

| 特性 | B+ 树 | LSM 树 |
|------|-------|--------|
| 写放大 | 中(原地更新) | 高(Compaction 重写) |
| 读放大 | 低 | 中(多层合并) |
| 空间放大 | 中(页填充) | 低(压缩 + 合并) |
| 写吞吐 | 中 | 高 |

**列式存储**:按列而非按行组织数据,利于压缩(同列类型一致)与分析聚合,适合 OLAP。Parquet、ORC、ClickHouse、Druid 采用列存;行存适合 OLTP 点查。

### 4.9 页 Page 与缓冲池 Buffer Pool

数据库以页(Page,通常 16KB/8KB)为最小 IO 单位。

- **Buffer Pool**:内存缓存热页,采用 LRU 变种(InnoDB 改良版 LRU,新生代/老年代)防止全表扫描污染。
- **脏页刷盘**:后台线程将修改页写回磁盘,结合 Double Write 防页断裂。
- **预读**:线性预读与随机预读,提升 IO 效率。

### 4.10 WAL 预写日志

WAL(Write-Ahead Logging)是保证持久性与原子性的基石:修改前先将日志顺序写盘,崩溃后通过日志重做(Redo)或回滚(Undo)恢复。

- **Redo Log**:物理日志,记录页变更,保证持久性。
- **Undo Log**:逻辑日志,记录旧值,支持回滚与 MVCC。
- **Checkpoint**:记录已刷盘位置,缩短崩溃恢复时间。
- **Group Commit**:合并多个事务日志刷盘,提升吞吐。

MySQL binlog(逻辑日志)用于主从复制与 PITR(Point-In-Time Recovery),与 Redo Log 通过两阶段提交保持一致。

## 五、分布式数据库

### 5.1 CAP 定理

CAP 定理(Brewer, 2000)指出分布式系统在网络分区时,只能在一致性(Consistency)与可用性(Availability)间二选一:

| 属性 | 含义 |
|------|------|
| 一致性 C | 所有节点同一时刻读到相同数据 |
| 可用性 A | 每个请求都能得到非错误响应 |
| 分区容忍 P | 网络分区时系统仍能运作 |

实践中 P 不可避免,故取舍在 C 与 A:

- **CP**:优先一致性,如 ZooKeeper、etcd、HBase。
- **AP**:优先可用性,如 Cassandra、DynamoDB、Eureka。
- **CA**:单机关系数据库,无分区问题。

### 5.2 BASE 理论 vs ACID

BASE 是 CAP 在工程上的折中,适用于大规模分布式系统:

| 缩写 | 含义 |
|------|------|
| BA | Basically Available 基本可用,允许降级 |
| S | Soft state 软状态,允许中间态 |
| E | Eventually consistent 最终一致性 |

ACID 追求强一致性,BASE 放弃即时一致性换取可用性与性能。金融核心账务用 ACID,社交、电商库存等场景常用 BASE + 最终一致性。

### 5.3 分布式事务

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 2PC | 协调者准备→提交/回滚 | 强一致 | 阻塞、单点、数据不一致风险 |
| 3PC | CanCommit→PreCommit→DoCommit | 降低阻塞 | 仍可能不一致,延迟高 |
| TCC | Try-Confirm-Cancel 业务补偿 | 无锁,高性能 | 业务侵入,需实现补偿 |
| Saga | 长事务拆分为子事务+补偿 | 适合长流程 | 最终一致,实现复杂 |
| 本地消息表 | 本地事务 + 消息 + 重试 | 简单可靠 | 耦合消息中间件 |
| Seata AT | 自动生成回滚 SQL | 透明 | 全局锁性能瓶颈 |

### 5.4 分片 Sharding

分片将数据水平或垂直切分到多节点,突破单机容量与吞吐瓶颈。

- **水平分片(Horizontal Sharding)**:按行切分,常用策略:
  - 哈希分片:hash(id) % N,分布均匀但扩容难(需一致性哈希)。
  - 范围分片:按时间/ID 区间,易扩容但热点。
  - 一致性哈希:节点增减只迁移部分数据。
- **垂直分片(Vertical Sharding)**:按列/表切分,如用户库与订单库分离。

分片带来的挑战:跨片 JOIN、分布式事务、全局唯一 ID(Snowflake)、扩容数据迁移。

### 5.5 复制与共识算法

复制(Replication)提升可用性与读吞吐,分三类:

| 模式 | 说明 | 冲突处理 |
|------|------|---------|
| 主从 Master-Slave | 主写从读,异步同步 | 单点主,简单 |
| 多主 Multi-Master | 多点可写 | 需冲突解决(版本向量/CRDT) |
| 共识 Paxos/Raft | 多数派写入 | 强一致,性能有代价 |

**Paxos**:Lamport 提出,Multi-Paxos 用于日志复制,理论严谨但实现复杂(Spanner、Chubby)。

**Raft**:更易理解,Leader 选举 + 日志复制 + 安全性约束,广泛用于 etcd、TiKV、CockroachDB、Consul。

### 5.6 一致性模型

| 模型 | 语义 | 典型系统 |
|------|------|---------|
| 强一致性 Strong | 读必见最新写 | Spanner、Paxos |
| 线性一致性 Linearizable | 强一致 + 全序 | etcd、ZK |
| 顺序一致性 Sequential | 同客户端保序 | ZooKeeper |
| 因果一致性 Causal | 因果相关保序 | DynamoDB |
| 读己之写 Read-Your-Writes | 客户端必见己写 | 主从 + 粘性会话 |
| 最终一致性 Eventual | 稳态后收敛 | Cassandra、DNS |

### 5.7 NewSQL

NewSQL 旨在兼顾 NoSQL 的扩展性与关系数据库的 ACID 与 SQL,代表产品:

- **Google Spanner**:全球分布,Paxos 复制,TrueTime 原子钟实现外部一致性。
- **TiDB**:计算存储分离,TiKV(Raft + RocksDB)存储,兼容 MySQL 协议。
- **CockroachDB**:Raft 复制,多活强一致,兼容 PostgreSQL 协议。
- **OceanBase**:蚂蚁集团,Paxos,金融级分布式数据库。

典型架构:SQL 层 + 分布式 KV 层 + 共识协议,水平扩展且保持 ACID。

## 六、NoSQL 与数据仓库

### 6.1 NoSQL 四类对比

NoSQL(Not Only SQL)为应对大数据与高并发,牺牲部分一致性换取扩展性,分四类:

| 类型 | 数据模型 | 典型产品 | 适用场景 | 弱点 |
|------|---------|---------|---------|------|
| 键值 Key-Value | 哈希表 | Redis、DynamoDB | 缓存、会话、计数 | 无结构查询 |
| 列族 Column-Family | 行键+列族 | Cassandra、HBase | 时序、宽行写入 | 查询灵活性低 |
| 文档 Document | JSON/BSON | MongoDB、CouchDB | 内容管理、配置 | 事务较弱 |
| 图 Graph | 节点+边 | Neo4j、JanusGraph | 社交、推荐、反欺诈 | 大规模分布式难 |

Redis 属键值,但提供 List、Hash、ZSet 等丰富结构,单线程内存模型性能极高。

### 6.2 列式存储 Parquet / ORC

列式存储将同一列连续存放,利于压缩与向量化执行:

- **Apache Parquet**:Dremel 论文实现,嵌套数据支持,RLE、字典、Snappy 压缩。
- **Apache ORC**:Hive 优化,轻量级索引(布隆、min/max),压缩率更高。

列存优势:只读所需列、同列类型一致压缩率高、向量化批量执行。劣势:单行更新难,适合只读分析。

### 6.3 数据仓库 vs 数据湖

| 维度 | 数据仓库 | 数据湖 |
|------|---------|--------|
| 数据 | 结构化,清洗后 | 原始,结构化+半结构化+非结构化 |
| 模式 | Schema-on-Write | Schema-on-Read |
| 用户 | 业务分析师 | 数据科学家 |
| 存储 | 关系型,成本高 | 对象存储(S3/HDFS),成本低 |
| 质量 | 高,治理完善 | 参差,需治理 |

数据湖仓(Lakehouse)趋势:Databricks Delta Lake、Apache Iceberg、Hudi 融合两者,在对象存储上提供事务、版本、Schema 管理。

### 6.4 OLTP vs OLAP

| 维度 | OLTP | OLAP |
|------|------|------|
| 全称 | 联机事务处理 | 联机分析处理 |
| 负载 | 短事务,高并发 | 复杂查询,大数据集 |
| 数据量 | GB~TB | TB~PB |
| 操作 | 增删改查 | 聚合分析,少更新 |
| 索引 | B+ 树 | 列存 + 位图 |
| 设计 | 规范化 | 反规范化/星型 |
| 产品 | MySQL、Oracle | ClickHouse、Greenplum |

### 6.5 星型模型与雪花模型

数据仓库多维建模的两种范式:

- **星型模型(Star Schema)**:中央事实表连接多个维度表,维度表反规范化。查询简单,JOIN 少,适合 OLAP。
- **雪花模型(Snowflake Schema)**:维度表进一步规范化为多表,节省空间但 JOIN 多,性能略差。
- **事实星座(Fact Constellation)**:多事实表共享维度,适合复杂业务。

事实表存度量(销售金额、数量),维度表存描述(时间、商品、地域)。

### 6.6 ETL vs ELT

| 模式 | 流程 | 特点 |
|------|------|------|
| ETL | 抽取→转换→加载 | 转换在中间层,数据仓库承载小 |
| ELT | 抽取→加载→转换 | 转换在数仓内,利用 MPP 算力 |

云数仓(Snowflake、BigQuery、Redshift)推动 ELT 成为主流,工具如 dbt 做转换层。开源工具:Airbyte、Fivetran(抽取)、Airflow、Dagster(调度)。

### 6.7 Hive / Spark SQL / Presto

| 引擎 | 定位 | 特点 |
|------|------|------|
| Hive | 批处理 SQL | MapReduce/Tez,延迟高,适合 ETL |
| Spark SQL | 内存计算 | DataFrame/DataSet,比 Hive 快 |
| Presto(Trino) | 交互式查询 | MPP,联邦查询多数据源,秒级响应 |
| ClickHouse | OLAP 列存 | 向量化执行,单表聚合极快 |
| Flink | 流批一体 | 流式 SQL,低延迟,状态计算 |

Hive 适合离线批处理;Spark 是通用计算引擎,SQL 为其模块;Presto/Trino 适合交互式即席查询;ClickHouse 适合实时分析;Flink 适合流式 ETL。

### 6.8 HTAP 混合负载

HTAP(Hybrid Transactional/Analytical Processing)在单一系统同时支撑 OLTP 与 OLAP,消除数据搬运延迟:

- **TiDB + TiFlash**:行存 TiKV 处理事务,列存 TiFlash 异步复制,通过 Raft Learner 保持一致。
- **CockroachDB**:多区域部署 + 改进执行器。
- **Oracle Exadata**:内存列存 + 智能扫描。
- **SingleStore**:内存行存 + 列存结合。

挑战在于资源隔离(事务与分析负载争抢 CPU/IO)与数据新鲜度(实时同步列存)。TiDB 通过 Learner 副本实现强一致只读分析,是当前较成熟的 HTAP 方案。

数据库技术从关系模型的数学优雅,到分布式一致性的工程权衡,再到 NoSQL 与 HTAP 的多元演进,始终在一致性、可用性、性能三角中寻找平衡。理解其底层原理——从 B+ 树、MVCC、WAL 到 Raft、LSM、列存——方能根据业务特征选型与调优,在工程实践中做出合理决策。
